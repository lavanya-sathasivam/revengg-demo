== IN-DEPTH DEFECT ANALYSIS

--- impact.py ---

DEFECT 1: Called functions that are NOT DEFINED
  The counterfactual() function's elif chain calls these functions
  which have NO definition anywhere in the codebase:
    _fee_counterfactual      (line 986)  - called when ctype=="fee"
    _interest_counterfactual (line 990)  - called when ctype=="interest"
    _termination_counterfactual (line 992) - called when requested_type=="termination"
    _removal_counterfactual  (line 998)  - called when requested_type=="removal"
    _replacement_counterfactual (line 1000) - called when requested_type=="replacement"
  → If any of these code paths are ever reached (e.g., via API request
     with change_type="fee"), a NameError will crash the server.

DEFECT 2: analyze_change() does NOT pass change_type to counterfactual()
  The api_b.py route passes req.change_type in the Pydantic model, but
  the analyze_change() function signature does not accept it:
    def analyze_change(contract_id, changed_sec, old_value, new_value,
                       expected_clause_sha256=None):
  And the call inside it does not pass change_type:
    cfact = counterfactual(contract_id, changed_sec, old_value, new_value)
  → The change_type parameter is silently ignored. The counterfactual()
     function defaults to requested_type = change_type or ctype, but since
     change_type is always None (not passed), it always uses the clause's
     actual type. The UI dropdown has 8 options but NONE of them affect
     the analysis.

DEFECT 3: _validate_change_values integrates new change_type but with risk
  The _validate_change_values function references changed.get("type") to
  determine SLA range validation. The new change_type constants are
  integrated, but the logic for non-payment/SLA types simply preserves
  existing behaviour (no arithmetic modelled). This is correct but the
  transition from unmodelled to modelled for "notice" has broken the
  test_status_taxonomy test.

--- api_b.py ---

DEFECT 4: change_type field exists but is NOT threaded through
  The ImpactRequest model has:
    change_type: str | None = Field(None, description="...")
  But the analyze() route does not pass it:
    report = impact.analyze_change(
        req.contract_id, req.clause_id, req.old_value, req.new_value,
        expected_clause_sha256=req.expected_clause_sha256,
    )
  → req.change_type is completely lost. The field exists in the model
     but has no effect on the engine.

DEFECT 5: No validation of change_type value
  The model accepts any string for change_type. There is no validator
  to restrict it to the 8 catalogue values. A caller could submit
  change_type="unknown_type" and the engine would infer from the clause
  type, potentially producing confusing results.

--- templates/index.html ---

DEFECT 6: UI change_type dropdown does NOT send value to API
  The HTML has a <select id="change-type"> with 8 options, but the
  JavaScript run() function sends this payload to /impact:
    var payload = {
      contract_id: ...,
      clause_id: ...,
      old_value: ...,
      new_value: ...,
    };
  → No change_type field is included. The 8 dropdown options are
     purely cosmetic; they do not affect the API request.

DEFECT 7: No UI JavaScript handler for change type selection
  There is no onchange handler on the change-type <select> element that
  updates any state or sends the selection to the server. The dropdown
  exists but is non-functional.

FAILURE: test_status_taxonomy_is_explicit_for_supported_and_unmodelled
  Error: AssertionError: 'partially_supported' != 'unsupported'

  Root cause: The test changes clause "3" (typed "notice") from 7 to 5 days.
  Before the Phase 5B changes, this code path fell into the else clause
  of counterfactual() and returned UNSUPPORTED status (no rows, no notes
  from the engine). The test was written expecting this behaviour.

  After the changes: _notice_counterfactual() is now called (the new
  elif branch for requested_type=="notice") and it produces rows + notes.
  The _counterfactual_status() function then sees "notes is not empty" and
  returns PARTIAL instead of UNSUPPORTED.

  This is a behavioural change caused by adding notice counterfactual
  support. The test needs updating to expect PARTIAL instead of UNSUPPORTED
  for notice-type clauses, but per instructions, no code/test changes
  are to be made during this inspection.
