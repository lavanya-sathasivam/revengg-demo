## Method, and the honest limits of these numbers

- The annotations in `data/ground_truth.json` were written by reading the two contract texts clause by clause, before running the system against them.
- The rule table and the annotations were written by the same team, on two synthetic contracts. A perfect score here means *internal consistency and rule coverage*, NOT validity on real contracts. Expect these numbers to fall on a real, messier document.
- What these numbers DO give the report: a regression guard, and a named list of the places where the engine is known to fail (below).
- These metrics cover the deterministic engine only. The LLM gap-filling path, the legal retrieval and the reasoning narrative are not scored here.
- For the record: the LLM path was exercised live on 2026-10-20. Asked about Clause 3.3, whose type pair (other, other) is not in the relation table, the model returned a `depends_on` edge to Clause 17.1 plus a condition node - a real dependency the typed table could not produce, and legally the right one. Those edges are NOT in the numbers below: the structural engine is deterministic and the LLM only ever adds to it.

### Defects this harness has already caught

- 2026-10-20 - `notice_vs_cure` never fired: the doubt rule read the heading-only section anchor '14. NOTICES' instead of Clause 14.1, found no day count, and skipped the doubt silently. Fixed in `impact.py`.
- 2026-10-20 - 15 clause-type errors: keyword matching was substring-based, so 'term' matched 'termination' and the bare word 'payment' could not be used as a heading cue. Fixed in `clauses.py` (word-boundary matching + heading cues).
- 2026-10-20 - a 'fee'-typed clause that imposes no fee (Clause 8.3) created a 'pay late charges' obligation, putting a false statement about the contract into the impact report. Fixed in `graph.py`.
- 2026-10-20 - every payment-typed clause was given the same 'pay the amount stated in each undisputed Invoice' node, which is false for Clause 7.1 (an invoicing duty) and for Clause 7.3 (where the Customer may withhold the disputed part), and Clause 7.2 was given a 'notify the Supplier of a dispute' deadline because 'undisputed' contains 'dispute'. Fixed in `graph.py` and `clauses.py`.

## Known gaps (measured, not assumed)

- Rupee amounts are parsed only where the service-credit counterfactual needs them (`clauses.find_amounts`). The general number parser still understands only days / months / years / %, so a rupee figure is not surfaced as a clause number anywhere else.
- The inverse dependency rule (where the REFERENCED clause is the dependent) currently covers one type pair, sla -> fee. It exists because the relation table otherwise assumes the referring clause is always the dependent.
- Clauses typed 'other' create no node, so a duty stated outside the typed families (for example Clause 3.1, 'provide the Services with reasonable skill and care') is not surfaced as an obligation.
- The counterfactual is implemented for payment-period changes and service-level changes. Any other change type says so instead of inventing rows.
- The doubt engine is a rule engine with a fixed set of doubt codes, not a general defeasible-reasoning system.
