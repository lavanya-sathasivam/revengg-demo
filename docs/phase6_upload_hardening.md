# Phase 6 Upload and PDF-Processing Hardening

**Status:** Implemented for local/test use. The configurable limits and failure
semantics are approved for local/test only. This is **not** production policy,
malware protection, parser sandboxing, OCR, or a hard resource quota.

**Scope:** `app_config.py`, `api_a.py`, `extract.py`, `application.py`,
`app.py`, the Phase 6 test suite, and the related configuration and operating
documentation.

**Decision record:** The local/test limits were approved through the Phase 6
acceptance instruction on 2026-10-23. The named approver was not provided. See
D14 and the still-open OQ-04 in
`docs/DECISIONS_AND_OPEN_QUESTIONS.md`.

---

## 1. Threat model covered

The upload path treats the browser, filename, declared MIME type, and PDF
contents as untrusted. It covers:

- files with a non-PDF extension;
- `.pdf` names containing non-PDF or misleading content;
- malformed, truncated, structurally repaired, or encrypted PDFs;
- PDFs with no extractable text, such as image-only scans;
- oversized uploads and oversized extracted text;
- PDFs with too many pages;
- parser work that runs past the cooperative deadline;
- path-traversal and hostile display filenames;
- anonymous and role-restricted uploads;
- cross-firm storage assignment;
- parser exceptions that contain paths or internal detail;
- database or publication failures after a file has been staged;
- abandoned temporary files from an interrupted earlier process;
- preservation of an existing published graph when a later upload fails.

It does **not** cover malware detection, parser sandboxing, hostile-code
isolation, OCR, password-protected PDFs, hard pre-emptive timeouts, hard memory
quotas, rate limiting, or production object storage. Those remain open or out
of scope.

## 2. Limits

| Setting | Local/test default | Enforcement |
|---|---:|---|
| `REVENGG_UPLOAD_MAX_BYTES` | 10,485,760 bytes (10 MiB) | Streaming copy; also checked from `Content-Length` when present |
| `REVENGG_UPLOAD_MAX_PAGES` | 200 | Checked after opening, before page text is read |
| `REVENGG_UPLOAD_MAX_EXTRACTED_CHARS` | 1,000,000 | Accumulated page by page; rejects before continuing |
| `REVENGG_UPLOAD_MAX_PROCESSING_SECONDS` | 30 | Cooperative deadline checked before opening, between pages, and after extraction |

All values must be positive integers. Invalid or non-positive environment
values fail settings construction with `ConfigurationError`; they are not
silently replaced. Settings are read only in upload mode. The values are
configurable and are not represented as approved production limits.

The deadline is deliberately described as **cooperative**. Python cannot
pre-empt a single parser call that hangs. A hard timeout would require running
the parser in a separate worker process with its own resource controls, which
is not implemented or claimed here.

The staged file is read once into memory for PyMuPDF parsing. Its size is
bounded by the upload limit before extraction. This also avoids a Windows file
handle remaining open when a malformed PDF fails to open, which previously
could prevent deletion of rejected bytes. The parser itself is not sandboxed
and does not have a separate hard memory quota.

## 3. Processing sequence

1. The request middleware establishes authentication and firm scope.
2. The upload route checks the active firm and upload role before staging bytes.
3. The display filename is sanitised to a metadata-only name.
4. A non-`.pdf` extension is rejected before any upload bytes are staged.
5. When `Content-Length` is present and clearly over the limit, the request is
   rejected before staging.
6. The body is streamed in 1 MiB chunks to
   `<upload_root>/.upload-<random>.part`, with a running SHA-256 and byte count.
7. The magic bytes, parser open, encryption state, repair state, page count,
   page text, text limit, and cooperative deadline are checked.
8. Only an accepted document is moved atomically to
   `<upload_root>/firm-<firm_id>/<uuid>.pdf`.
9. The contract row, immutable first version, trace, and success audit event are
   committed together.
10. Clauses are persisted and the graph is built. A graph failure leaves any
    previously published graph intact.

The original filename is never used as a filesystem path. A UUID generated by
the server is the only stored basename.

## 4. Failure semantics

| Failure | HTTP result | Contract/version | Stored bytes | Audit |
|---|---|---|---|---|
| Wrong extension | `400` | None | None | `upload.rejected` |
| Empty upload | `400` | None | None | `upload.rejected` |
| Oversized upload | `413` | None | None | `upload.rejected` |
| Non-PDF bytes named `.pdf` | `422` | Failed contract + failed version | None | `contract.extraction_failed` with `reason_code` |
| Malformed or repaired PDF | `422` | Failed contract + failed version | None | `contract.extraction_failed` |
| Encrypted PDF | `422` | Failed contract + failed version | None | `contract.extraction_failed` |
| No extractable text | `422` | Failed contract + failed version | None | `contract.extraction_failed` |
| Page limit exceeded | `413` | Failed contract + failed version | None | `contract.extraction_failed` |
| Text limit exceeded | `413` | Failed contract + failed version | None | `contract.extraction_failed` |
| Processing deadline exceeded | `422` | Failed contract + failed version | None | `contract.extraction_failed` |
| Unexpected parser exception | `500` | None | None | `upload.processing_failed` |
| Database/publish failure | `500` | None or no partial commit | Published file removed if necessary | `upload.processing_failed` |

For a failed content/parse result, the version keeps the sanitised source
filename, SHA-256, byte size, `application/pdf` expected source type, failed
extraction status, failed version status, provenance class, and creator. It has
no `source_path`, no raw text, no clauses, and no graph. The audit reason code
is one of the stable values defined in `extract.py`:

- `not_a_pdf`
- `malformed_pdf`
- `encrypted_pdf`
- `no_extractable_text`
- `page_limit_exceeded`
- `text_limit_exceeded`
- `processing_timeout`
- `extraction_failed`

Parser internals, file paths, and document text are never returned to the
client. Unexpected parser exceptions are logged for operators but the HTTP
response is a generic `500`.

Rejected bytes are deleted rather than published. The deletion path is
best-effort: a filesystem failure is logged, while the database record and audit
event still reflect the rejection. The startup cleanup removes only top-level
`.upload-*.part` files left by an interrupted process; it never touches accepted
documents, firm directories, the database, or non-matching files.

## 5. Storage and provenance

Accepted files use:

```text
<upload_root>/firm-<firm_id>/<uuid>.pdf
```

The firm is derived from the authenticated session, never from a client field.
Paths are resolved and checked to remain under the configured upload root
before use. Published names do not include the user's filename.

The first immutable version records:

- safe source filename;
- generated source path for accepted files;
- SHA-256 and byte size;
- expected MIME type;
- extraction status;
- splitter version for accepted imports;
- provenance class;
- version lifecycle status and creator.

The append-only audit trail records lifecycle events and sanitised rejection
metadata. It never records contract text, clause text, session tokens, parser
detail, or file contents. Existing Phase 5 version-history and
last-known-good-graph behavior is unchanged.

## 6. Compatibility

- Existing `POST /upload` response fields and success flow are preserved.
- Corrupt `.pdf` content still returns `422` and records no clauses, now with a
  safe failed version and reason code.
- Non-PDF extensions still return `400` without a contract row.
- Demo mode remains anonymous, read-only, and unable to upload; it never creates
  an upload directory.
- Existing root compatibility suites continue to pass.
- `app.py` re-exports the new staging, publishing, cleanup, and error types for
  historical import paths.
- No schema migration is required for Phase 6; the existing Phase 5 version
  columns carry the failure provenance.

## 7. Tests

Focused suite:

```powershell
py -3.11 -m unittest discover -s tests -p "test_phase6_upload_hardening.py" -v
```

Full local regression:

```powershell
py -3.11 -m unittest discover -s tests -v
py -3.11 -m unittest test_api test_db_clauses test_reasoning test_retrieval test_split_clauses -v
git diff --check
```

The focused suite covers:

- defaults and environment overrides for all four limits, plus fail-closed
  invalid values;
- valid extraction and rejected non-PDF, malformed, repaired, encrypted, and
  no-text PDFs;
- page, text, and cooperative-time limits, including each deadline check
  position;
- wrong extension, empty body, actual streaming-size limit, and pre-staging
  rejection;
- server-generated firm-scoped storage names and traversal filenames;
- failed-version hash/size/name provenance with no stored file or clauses;
- sanitized parser and database failures, temp cleanup, and no partial
  publication;
- anonymous and reviewer denials, demo compatibility, and audit events;
- startup cleanup of abandoned staging files without deleting accepted files;
- preservation of an existing published graph across a failed upload.

**Acceptance run (2026-10-23):** the Phase 6 focused suite passed 33 tests; the
full `tests/` suite passed 236 tests; the additional root compatibility suites
passed 104 tests with 4 skipped (the four skips require a pre-existing local
`app.db`, which this work did not create). `git diff --check` was clean. These
are local SQLite/test results, not production validation.

All tests use temporary databases and upload directories. They do not open or
modify `demo.db`, `app.db`, the real `uploads/` directory, or `.env`.

## 8. Residual risks and open decisions

- Production upload size/page/text/time limits and partial-extraction policy are
  not approved (OQ-04).
- No malware scanner, antivirus integration, sandbox, or content-disarm
  control exists. Do not claim that uploaded files are malware-free.
- The timeout is cooperative, not a hard kill. A parser call can still hang or
  consume memory within the process.
- The parser receives a bounded in-memory copy; the bound is the configured
  upload size, not a separate hard memory quota.
- No OCR is implemented. Image-only scans are rejected.
- No password authentication for encrypted PDFs is implemented; they are
  rejected.
- No rate limiting or per-firm upload quota is implemented.
- SQLite and the local filesystem remain local/test storage, not production
  multi-tenant or object storage.
- Rejected-byte deletion is best-effort at the filesystem level; a deletion
  error is logged and can leave an abandoned staging file for startup cleanup.
- Storage confinement is checked in-process. It is not a substitute for
  OS-level filesystem permissions or production object-storage policy.
- FastAPI parses the multipart `UploadFile` before the endpoint runs. An
  anonymous or role-denied request is rejected before staging or storage, but
  the framework may already have buffered or spooled the request body. Bound
  request bodies at the reverse proxy or server as well; the endpoint's limits
  do not protect unauthenticated requests from that buffering.
- Startup staging cleanup has no age or owner check. It assumes no other
  process is writing to the same upload root; multi-instance or rolling
  deployments would need coordination.
